## 1. Introduction｜緒論
大多數程式並非由專業開發者撰寫，而是由各領域的人為了自己的目標而寫，例如老師的成績試算表、設計師的介面原型。他們與專業開發者的差別在於目標：專業者被付錢來交付並長期維護軟體，終端使用者則是為了領域內的其他目標。然而他們面對同樣的軟體工程問題，而且錯誤可能造成真實損失（例如試算表公式錯誤導致企業損失）。本文界定 [[end-user software engineering]]（EUSE）這個領域：有別於一般 end-user programming 研究關注「如何建構程式」，EUSE 關注建構以外的品質活動。作者觀察到：實證研究涵蓋的族群很廣，但工具研究過去集中在試算表與事件式程式，且偏重測試與除錯，近年才擴展到網頁、行動裝置與需求、規格、再利用等面向。

## 2. Definitions｜定義
- **2.1 Programming and Programs（程式設計與程式）**：把程式定義為「可接受變動輸入、可由具計算能力的裝置執行的一組規格」；因此錄影機設定、HTML/CSS 也算程式。
- **2.2 End-User Programming（終端使用者程式設計）**：定義為「主要為了個人而非公開使用而寫程式」。關鍵在於意圖而非身分、經驗或語言：同一位會計師在家做的試算表與在公司共用的試算表性質不同；資深工程師寫給自己用的輔助程式也算。這個區分是連續的，且可能改變：原本只給自己用、未經測試的程式，一旦被他人使用，就會突然需要更嚴謹的工程處理。本節也區辨了 end-user development、customization、tailoring、視覺化程式、領域特定語言與腳本等相關詞彙。
- **2.3 End-User Software Engineering（終端使用者軟體工程）**：專業與終端使用者軟體工程的差別，在於對軟體品質投入多少注意力。作者以表格對照：在需求、規格、再利用、測試、除錯各項，專業者分別是明確、明確、有計畫、謹慎、有系統的；終端使用者則是隱含、隱含、無計畫、過度自信、隨機應變的。EUSE 研究的挑戰是把工程活動融入使用者既有的工作流程，而不要求他們改變工作重心。

## 3. End-User Software Engineering Research｜EUSE 研究回顧
依軟體工程教科書的活動分類整理文獻，並從終端使用者的角度重新詮釋；作者強調這些活動並非依序發生。另外說明本文不處理程式的實作與使用本身，[[maintenance]] 則放在 3.3 的分享議題中討論。
- **3.1 What Should My Program Do?——Requirements（需求）**：終端使用者很少明確陳述需求，需求常在實作過程中才浮現，而且因為只需要跟自己協商，變動得更頻繁。需求也因情境而異：辦公室多為自動化重複作業；家中多為安排未來的動作，或是沒有明確目的的「修修補補」；線上情境則開始需要考慮他人。
- **3.2 How Should My Program Work?——Design and Design Specifications（設計與規格）**：終端使用者常是沒受過設計訓練的「沉默設計師」，而且不認為自己的程式會被長期使用，雖然這個預期往往不準確（例如企業試算表會愈長愈大）。小節涵蓋設計流程、撰寫規格與推論規格三種取向。
- **3.3 What Can I Use to Write My Program?——Reuse（再利用）**：對終端使用者而言，再利用常是專案能否進行的關鍵。小節涵蓋尋找可再利用的程式碼、使用 API 的困難（引用 Ko et al. 2004 的學習障礙）、建立與分享可再利用程式碼，以及為終端使用者設計合適的抽象。其中特別指出：使用者常把自己的程式當成用完即丟，但這些程式常意外地長期存活並被他人複製改用，而原作的改進不會傳遞到副本上。
- **3.4 Is My Program Working Correctly?——Verification and Testing（驗證與測試）**：核心問題是 [[overconfidence]]：試算表研究一再發現使用者錯誤率高卻對正確性過度自信，較容易把錯的值判為對。小節涵蓋判斷正確性的來源、測試（如 WYSIWYT）、依規格檢查、一致性檢查（如單位推論）與視覺化。
- **3.5 Why is My Program Not Working?——Debugging（除錯）**：除錯本質上是提出與驗證假設的診斷活動；終端使用者常不清楚程式如何執行，且傾向改到看起來能動為止，反而引入更多錯誤。小節涵蓋相依性分析（如 Whyline）、自動修改建議、整合多種推理，以及社會與認知支援（例如兩人一起除錯較有系統）。

## 4. Cross-Cutting Issues in End-User Software Engineering｜跨領域議題
- **4.1 Risk, Reward, and the Role of Domain（風險、報酬與領域）**：以 Blackwell 的 [[attention investment]] 模型說明使用者會權衡效益、回報、成本與風險；不做嚴謹的需求分析未必是懶惰，而可能是合理的投資判斷。領域的複雜度、使用者對領域的熟悉程度，以及協作與文化脈絡，也都影響使用者是否投入工程活動。
- **4.2 Persuading People to Use EUSE Tools（說服使用者使用 EUSE 工具）**：使用者可能覺得新功能有風險或無用。作法之一是訓練，另一種是在情境中創造「可教時刻」，例如「驚訝—解釋—獎勵」策略：用出乎意料的視覺提示引起好奇、提供解釋、再給予回饋獎勵；但也要防範使用者只為了達成表面指標而操作。
- **4.3 Self-Efficacy, Gender, and Strategy in EUSE Tool Use（自我效能、性別與策略）**：自我效能與解題策略會影響工具的效果；研究發現女性的自我效能能預測其除錯功能使用成效，而修修補補（tinkering）的方式與效果也有性別差異。

## 5. Conclusions｜結論
EUSE 研究早期集中在試算表與事件式語言的測試除錯，現正朝更多平台（尤其是網頁）、更多工程面向與特定應用領域擴展。作者提問：不同族群需要的是根本不同的工程支援，還是同一套概念針對領域的調整？並提醒終端使用者的程式只是他們生活中的一小部分，理解程式如何嵌入日常，才能理解人們為何寫程式。

## Relevance to This Study｜與本研究的關聯
- **「意圖」定義可以對應生成物的處境**：依本文定義，使用者為自己生成的互動物件屬於 end-user programming 的產物，即使程式碼是 AI 寫的；而作者特別指出，原本只給自己用的程式一旦被長期使用或分享，就需要更多工程處理。這正是 AI 生成物從「一次性」走向「持續使用」時會遇到的轉折（推論）。
- **生成物可能繼承 EUSE 的所有弱點**：需求隱含且邊做邊變、沒有規格、對正確性過度自信、除錯靠反覆嘗試。AI 生成讓使用者跳過了寫程式，卻沒有解決這些品質問題，甚至可能加劇，因為使用者連程式內容都沒讀過（推論）。
- **用完即丟卻意外長壽**：3.3 指出終端使用者低估程式的存活時間。本研究可以反過來看：AI 生成物多半被當成用完即丟，而少數被留下的，可能正是那些「意外」變得長期有用、並開始需要維護的物件，值得作為訪談對象（推論）。
- **說服使用者投入的設計策略**：4.2 的「驚訝—解釋—獎勵」提供一種思路：生成式工具或許能在適當時機提示使用者檢查、保存或整理生成物，而不是只強調生成的速度（推論）。
- **與 Blackwell (2002)、Ko et al. (2004) 串接**：本文把注意力投資與學習障礙整合進同一個框架，可作為本研究 Related Work 中 EUP/EUSE 段落的總綱引用（推論）。
