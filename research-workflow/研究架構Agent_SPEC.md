## 1. 為什麼要這個 agent

Agent 4（研究設計）會直接把你的 Problem/Aim/Objectives 落成訪談大綱、招募條件等執行細節。但如果 Problem/Aim/Objectives 本身邏輯不一致、或其實沒有真正回應 Agent 1 Stage C 找到的研究缺口，後面所有的訪談設計都會建立在錯的地基上。這個 agent 插在中間，先做兩件事：**核對地基**（邏輯自洽＋缺口對齊），確認沒問題後才**規劃整體框架**（framework）——把這個研究要用什麼構念、方法、資料、分析串成一張圖，讓你在真的去設計訪談大綱之前，先看到整個研究的骨架長什麼樣。

## 2. 輸入

- 你目前的 Problem / Aim / Objectives 草稿（可能來自 Agent 2 精讀報告啟發、也可能是你自己已經有的版本）
- Agent 1 Stage C 產出的研究缺口卡片（「為什麼沒人做／有沒有價值／能產生什麼貢獻」）。**已定案，新增備用路徑**：如果這個主題還沒有走完整的 Agent 1 流程，也可以直接採用某篇你已精讀的論文（Agent 2 產出）自己在 Conclusion／Limitations 裡明確承認的樣本限制或未來研究建議，當作替代的研究缺口輸入——這跟走完整 Agent 1 流程一樣合法，只是缺口來源從「跨文獻歸納」換成「單篇論文自陳」，一樣要照同一套三個問題（為什麼沒人做／有沒有價值／能產生什麼貢獻）整理清楚
- Agent 2 精讀報告——**已修正**：不是只挑一篇當佐證，而是讀整個主題資料夾底下 `01_文獻探討/critical-form/` 的所有論文報告（見 [研究主題Repo_資訊架構.md](研究主題Repo_資訊架構.md)）。如果這個資料夾裡有多篇論文，Stage A 開始前先花一小段做簡短彙整（每篇論文跟目前 Problem 的關聯是什麼），再進入邏輯評判，避免只看了其中一篇就下判斷

## 3. Pipeline 設計：三階段

跟前面幾個 agent 一樣的邏輯：機械式核對跟需要學術判斷的地方分開，你在關鍵節點確認過才繼續。

### Stage A — 邏輯與缺口對齊評判（推論，待你確認）

對你的 Problem/Aim/Objectives 草稿做三項檢查，**每一項都明確標「推論」**，不是定論：

1. **Problem 與 Aim 是否對應一致**：Aim 是不是真的在回答 Problem 提出的問題，而不是答非所問
2. **Objectives 是否真的能達成 Aim**：有沒有多餘的 Objective（跟 Aim 無關）或不足的 Objective（Aim 沒被完整涵蓋）
3. **是否真的對應到 Agent 1 找到的研究缺口**：這組 Problem/Aim/Objectives 是不是真的在填補 Stage C 卡片裡標出的那個缺口，而不是憑空另起爐灶、繞過已經找到的缺口

輸出逐項評判意見（哪裡邏輯一致、哪裡可能有落差），**人工 review 點**：你確認評判有沒有道理，決定要不要修改 Problem/Aim/Objectives，明確跟我說「可以規劃框架了」才進 Stage B。

### Stage B — 你確認或修正

你看過 Stage A 的評判，直接修改 Problem/Aim/Objectives（或跟我說怎麼改），確認地基穩了才繼續。**這一步不能省略**——這是整條 pipeline 裡少數容許你「打掉重練」的節點，晚一點在 Agent 4（研究設計）才發現地基有問題，成本高很多。

### Stage C — 框架規劃＋流程圖

輸入 Stage B 確認後的 Problem/Aim/Objectives，規劃研究框架，包含：

- **理論構念**：這個研究要用哪些關鍵構念/變項（可從 Agent 1/2 已蒐集的文獻歸納）
- **方法選擇**：質化/量化/混合，以及為什麼這個方法能回答 Problem
- **資料蒐集規劃（概要）**：要蒐集什麼類型的資料、從誰、用什麼形式——這裡只是高層次規劃，不是逐字訪談大綱，**細節留給 Agent 4（研究設計）**（已定案：流程圖跟這裡的規劃都只畫到這個粒度，不重工 Agent 4 的範圍）
- **分析方法（概要）**：打算怎麼分析這些資料
- **預期貢獻**：呼應 Agent 1 Stage C「補上這個缺口能產生什麼貢獻」的答案
- **對照參考（已定案，新增）**：附帶列出 1-2 個 Agent 1/2 已經看過的相關論文的研究框架當對照（例如 Chen (2026) 論文 Figure 5 的概念框架），方便你判斷自己的框架站不站得住腳

**每一項決策都要附註三件事（已定案，新增）**——理論構念、方法選擇、資料蒐集規劃、分析方法，這四項每一項都不是只寫「選了什麼」，而要註記：
1. **原因**：為什麼選這個而不是其他選項
2. **限制**：這個選擇犧牲了什麼、有什麼做不到的地方
3. **影響**：這個選擇會怎麼影響後面 Agent 4 的執行細節，或影響研究結論能推論到多廣

這樣之後你或口試委員回頭檢視框架時，看得到「為什麼是這樣設計」，不是只看到一個沒有推理過程的成品。

再把上述元素串成一張**流程圖**（研究缺口 → Problem → Aim → Objectives → 框架構念 → 方法/資料/分析 → 預期貢獻），輸出 HTML。

### Stage D — 框架修正協作（新增，回應「框架站不住腳怎麼辦」這個缺口）

這一階段不是自動觸發，是**你發現不對勁時主動叫出來的討論**——例如訪談做到一半、或 Agent 5 洞見萃取跑出來的 Pattern 跟 Stage C 預期的構念對不上，你把這個落差告訴我，我們一起把它想清楚，而不是我直接吐一份「修正版框架」給你。

**輸入**：你觀察到的具體落差（例如「Pattern 顯示的規律跟我原本設的理論構念完全搭不上」「訪談根本問不出資料蒐集規劃裡預期的那種資料」）

**診斷流程**：先定位問題出在框架的哪一個環節，而不是籠統地說「框架不對」。常見的幾種偏誤類型，用來幫你我對話時快速對焦：

1. **構念定義誤判**：實際資料顯示某個理論構念根本不是受訪者理解這件事的方式（例如你預設「控制感」，但受訪者其實是從別的角度在談這件事）
2. **方法產出的資料類型不對**：選的方法蒐集不到能回答 Problem 的那種資料（例如訪談問不出行為性資料，其實需要觀察法或日記法）
3. **樣本/情境邊界條件不符**：Objectives 設定的母體特徵跟實際招募到、或資料裡浮現的母體其實不一樣，導致 Aim 沒辦法在這個樣本上被驗證
4. **構念之間的關係假設錯了**：預期構念 A 會影響構念 B，但資料顯示是反過來、或根本無關
5. **範圍設定過大或過小**：Objectives 涵蓋的範圍比 Aim 大或小，導致資料蒐集要嘛不夠、要嘛做了多餘的事
6. **文獻支撐不足（新增）**：框架裡的某個構念/方法選擇，在 `01_文獻探討/` 既有的文獻裡其實找不到支撐——這種情況不是改構念，而是**先退回 Agent 1/2 補查文獻**：可能是 Agent 1 Stage B/C 需要用新的關鍵字重跑一次，或是需要 Agent 2 精讀某篇特定新論文。等文獻補齊，回到 Stage A 重新評判一次，再決定要不要真的修正框架。這是原本設計唯一缺的一條路——之前只有「改框架」，沒有「先去補資料再回來看」

**討論方式**：針對你指出的落差，我會先明確講「這個落差比較像是上面哪一種類型」（或指出是不是新的類型），再提出 2-3 個修正方向，**每個方向都要註明是根據什麼**——是根據 `01_文獻探討/` 裡已經蒐集的文獻，還是根據你這次觀察到的實際資料本身——並老實講每個方向的代價（例如「改構念意味著要重新檢視 Objective 2」）。最終選哪個方向、要不要修正，由你決定。

**確定修正方向後**：
1. 更新 `02_研究問題/Problem_Aim_Objectives.md` 和/或 `03_研究架構/研究架構.html`，在 `00_編輯歷程.md` 記一筆里程碑（例如「因訪談發現 XX，把構念 A 換成構念 B」），git commit message 寫清楚修正理由，方便之後回溯為什麼會有這次修正
2. **檢查已完成的下游產出受不受影響**——如果 `04_研究方法/` 已經定稿、`05_原始資料/` 已經蒐集了一部分，我會明確跟你確認這些既有產出是不是還適用：
   - 如果構念/方法真的變了，**具體動作是拿新版框架重跑一次 [研究設計Agent_SPEC.md](研究設計Agent_SPEC.md) Stage C 的雙向可回溯性檢查**（不是只籠統說「檢查一下」）——用新構念/Objectives 重新核對訪談大綱，才知道哪些題目還站得住腳、哪些已經對不上
   - 已經蒐集的資料，要嘛重新檢視（哪些題目的答案在新構念下還算數）、要嘛在文件裡明確標註「基於 YYYY-MM-DD 修正前的框架版本」，不能默默假裝什麼都沒發生

## 4. 視覺樣板規格

沿用精讀陪讀 agent 的技術棧（Tailwind CSS＋FontAwesome，每個構念分區可以比照專屬配色的做法），額外加兩樣東西：

- **流程圖**：用 **Mermaid.js**（CDN 引入）畫，agent 只需要產生 mermaid 語法文字（節點與箭頭定義），瀏覽器會自動排版，不用手算 SVG 座標
- **版本紀錄／研究筆記**：**已定案改用 GitHub**，取代原本「靜態檔案＋操作規則」的折衷方案，見下方說明

### 版本紀錄與研究筆記的保存機制：改用 GitHub（已定案方向，細節待你補完）

你確認要發佈到雲端、用 GitHub 的形式，這比原本的折衷方案乾淨很多，因為：

- **版本紀錄＝ git commit history**：不用在頁面裡手刻一張 changelog 表格，每次調整框架就是一次 commit，commit message 就是異動摘要，`git log` 本身就是完整、不會出錯的版本紀錄
- **研究筆記＝直接編輯檔案再 commit**：你可以直接在 html（或另外分離的 notes 檔）裡寫筆記，因為有版本控制，就算之後某次重新產出不小心動到筆記段落，也能從 commit history 救回來，不需要靠「agent 每次都要記得保留」這種容易出錯的操作規則
- **發佈／檢視**：可以用 **GitHub Pages** 把 html 發佈成一個網址，效果跟你參考的唐老師講義頁面一樣，直接開瀏覽器連結就能看，不用在本機找檔案

這幾個實作細節**已定案**（原本是「每個主題各自一個 repo」，你後來改成一個大 repo 裝多個主題，見 [研究主題Repo_資訊架構.md](研究主題Repo_資訊架構.md)）：

- **repo 範圍：一個大 repo，裡面用資料夾分不同研究主題**——好處是跨主題查找、比較方便
- **Public/Private：Private**——不透過 GitHub Pages 發佈，網頁部分你自己手動在本機打開 html 檔案看，就跟現在這幾份 demo 檔案一樣，只是多了 git 版本控制。git 純粹做版本紀錄用，不用考慮 GitHub Pro 付費方案
- **要不要我幫你設定**：GitHub 帳號登入、repo 建立、第一次 push 這些操作，我可以引導你一步步做，但像「建立雲端 repo」「push 內容上去」這類會建立資料的動作，我會在真的要執行前明確跟你確認一次，不會自己直接動手

## 5. 輸出檔案位置

**已修正**：改成對應 [研究主題Repo_資訊架構.md](研究主題Repo_資訊架構.md) 的固定慣例——Stage A/B 的評判與確認結果寫入該主題資料夾的 `02_研究問題/Problem_Aim_Objectives.md`，Stage C 的框架寫入 `03_研究架構/研究架構.html`。agent 還是不會自己決定「是哪個主題資料夾」，那個要你明確指定，但資料夾底下該放哪個子路徑已經是固定慣例，不用你每次重新想檔名。
