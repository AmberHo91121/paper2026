# 步驟 3　研究架構（Research Framework Architect）SPEC

> 共通原則見 [AI_agent化工作流程草案.md](AI_agent化工作流程草案.md)。

## 目的

在進入研究設計前先核對地基：Problem／Aim／Objectives 是否邏輯一致、是否真的回應研究缺口；確認後再規劃整體框架，讓研究骨架先被看見。

## 輸入

- 使用者的 Problem／Aim／Objectives 草稿
- 研究缺口：`01_文獻探討/研究缺口.md`；**備用路徑**：已精讀論文在 Conclusion／Limitations 自陳的限制或未來研究建議，同樣依「為什麼沒人做／有沒有價值／能產生什麼貢獻」整理
- 主題 `papers/` 內所有已完成的 Critical Form；多篇時先簡短彙整每篇與 Problem 的關聯，再評判

## 階段（依序進行，每階段結束都停下等確認）

### 邏輯評判階段：邏輯與缺口對齊（推論） → `02_研究問題/Problem_Aim_Objectives.md`

1. Aim 是否真的回答 Problem
2. Objectives 能否達成 Aim（有無多餘或不足）
3. 是否對應到研究缺口，而非另起爐灶

### 地基確認階段：使用者確認或修正

**不可省略**，這是容許打掉重練的節點。使用者說「可以規劃框架了」才進框架規劃階段。

### 框架規劃階段 → `03_研究架構/研究架構.html`

- **理論構念**、**方法選擇**、**資料蒐集規劃（概要）**、**分析方法（概要）**：四項各附原因／限制／影響（影響含對步驟 4 與結論可推論範圍的影響）
- **預期貢獻**：呼應研究缺口
- **對照參考**：列 1–2 篇已讀論文的框架供比較
- **流程圖**（Mermaid.js）：研究缺口 → Problem → Aim → Objectives → 構念 → 方法／資料／分析 → 預期貢獻。只畫到構念層級，執行細節留給步驟 4
- 視覺沿用精讀報告樣式，範本：[研究架構_template.html](研究架構_template.html)。研究筆記區由使用者撰寫，重新產出時保留

### 框架修正階段（使用者主動叫出的協作討論）

**觸發**：使用者發現落差，例如步驟 4 技法蒐不到需要的資料、步驟 5 的 Pattern 對不上構念、編碼時發現訪談題目無效。

**先定位偏誤類型**：

1. 構念定義誤判：受訪者不是用這個構念理解這件事
2. 方法產出的資料類型不對
3. 樣本／情境邊界條件不符
4. 構念間關係假設錯誤
5. 範圍過大或過小
6. 文獻支撐不足 → **先退回步驟 1／2 補查**，補齊後回邏輯評判階段重評，再決定是否改框架

**再給 2–3 個修正方向**，註明依據（既有文獻或實際資料）與代價；由使用者決定。

**定案後**：

1. 更新 `02_研究問題/`、`03_研究架構/`（技法層級的問題則改 `04_研究方法/`），在 `00_編輯歷程.md` 記里程碑，commit message 寫明理由
2. 檢查下游：用新框架重跑步驟 4 定稿檢核階段的雙向可回溯性檢查；已蒐集的資料要重新檢視，或標註「基於 YYYY-MM-DD 修正前的框架版本」
