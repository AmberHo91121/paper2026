# 研究設計 Agent（Research Designer）— SPEC

> 對應 [AI_agent化工作流程草案.md](AI_agent化工作流程草案.md) 的 Agent 4。依討論結果定案：涵蓋更廣的設計研究方法（不限於可用性測試），`usability-test-planner` skill 是其中一種技法選項，不是整個 agent 的引擎。
> 沿用既有文件慣例：原本帶 ❓ 待確認欄位供你人工 review，目前已全部定案。

---

## 1. 為什麼要這樣設計

Agent 3 已經把「方法類別」跟為什麼選這個類別定案了（例如「質化方法」「Research through Design」，都附了原因/限制/影響）。Agent 4 的工作**不是再選一次方法**，而是把這個類別操作化成具體、站得住腳的執行工具——訪談大綱、招募條件、問卷題項等。同一個方法類別底下有很多技法（例如「質化方法」底下有半結構訪談、日記研究法、情境訪查、共同設計工作坊……），適用情境差很多，選錯技法會讓資料蒐不到框架真正需要的東西。這個 agent 要做兩件事：**選對技法**（符合情形），然後**把技法執行細節做得經得起檢驗**（支持性＋縝密性）。

## 2. 輸入

- Agent 3 產出的 `03_研究架構/研究架構.html`（方法選擇、理論構念、Objectives、資料蒐集規劃概要，含原因/限制/影響）
- 你提供的實務限制：時程、能接觸到的受訪者類型與規模、可用資源（工具、預算、場地）

## 3. Pipeline 設計：三階段

### Stage A — 技法提案（推論，待討論）

依 Agent 3 框架的方法類別，提案 2-3 個具體技法選項。**這裡才是真正需要「設計研究方法」判斷力的地方**，例如框架寫的是「質化方法」，agent 要判斷這個研究情境比較適合半結構訪談、日記研究法、情境訪查、共同設計工作坊，**還是需要伴侶/雙方都訪談的 dyadic 訪談**（新增：如果框架構念本身涉及關係中雙方的動態，例如「監控對稱性」這種需要看到雙方視角落差的構念，只訪談一方會看不到關鍵資料，dyadic 訪談要明確列為候選技法之一，不能只停在「半結構訪談」這種預設）——不能每次都預設走同一種。

每個技法選項附註：
1. **原因**：為什麼這個技法能操作化框架裡的方法選擇、回答 Problem。**新增要求**：這裡不能只憑直覺講，要盡量指出這個技法的方法論慣例出處——優先引用 `01_文獻探討/` 裡已經蒐集到的文獻（例如選日記研究法時，援引 Chen (2026) 論文引用 Bolger et al. (2003) 的日記法設計慣例），沒有現成文獻可引的話才用該技法領域公認的一般方法論慣例。目的是讓「選這個技法」跟「選框架構念」一樣有憑有據，不是憑經驗感覺帶過
2. **限制**：這個技法蒐不到什麼、有什麼做不到的地方
3. **影響**：對實際執行的資源需求（大概要幾位受訪者、要花多久、需要什麼前置準備）——排程/邀約這段原本規劃給一個排程協調 agent，已確認不需要，這部分你自己手動安排
4. **適用判斷**：跟你提供的實務限制（時程/受訪者可及性/資源）對不對得上

如果框架的方法類別剛好對應到「可用性測試」，這個選項會標註「可交給 `usability-test-planner` skill 走它既有的問答式共創流程」——那個 skill 已經做得不錯，不用重造。其他技法（日記法、情境訪查、RtD 相關技法等）目前沒有對應 skill，由這個 agent 自己的 Stage B 對話流程處理。

**人工 review 點**：你選定要用哪個技法，明確跟我說才進 Stage B。

### Stage B — 對話式共創執行細節

你選定技法後，用來回問答的方式一起把細節定案——訪談大綱題目、task scenario、招募條件、問卷題項（如果這個技法需要的話）。**這步照舊是「整個過程本來就是來回問答定案，不是事後審查」**，不會一次生成整份丟給你。

過程中每一題/每一條都要能講出「這在對應框架裡的哪個理論構念或哪個 Objective」——講不出來的，先擱置，不要為了湊題目硬塞。

**新增：研究倫理與知情同意**——這步一定要一起討論，不能等到定稿後才想到。至少要涵蓋：
- 這個研究需不需要送機構倫理審查（IRB）——你所屬機構有沒有要求、這個主題（尤其涉及性/別認同、健康資料等敏感資訊時）通常需不需要
- 知情同意書要涵蓋的重點：資料用途、保密方式、可以隨時退出、敏感資訊（例如本次案例的性向、經期健康資料）會怎麼被去識別化處理
- 招募文宣/邀請用語要不要避免讓潛在受訪者的身份被意外揭露（例如公開招募酷兒受訪者時的措辭考量）
- **新增：如果技法是 dyadic／伴侶雙方訪談**，要額外討論：雙方是不是都要各自獨立同意（不能只靠一方代替另一方同意）、要不要讓對方知道另一半也被訪談、訪談內容會不會意外向另一半揭露原本沒有分享的資訊（例如其中一方的追蹤資料或情感表述被間接透露給對方）

這不是選配項目——凡是這個 agent 產出訪談大綱/招募條件，就一定要有對應的倫理討論，尤其你目前實際在跑的案例（酷兒女性經期追蹤）本身就是敏感身份＋敏感健康資料的組合。

### Stage C — 定稿＋雙向核對＋嚴謹判準自我檢核

定稿前做兩件事，都是**推論，你覆核**：

**1. 雙向可回溯性檢查**
- 正向：每一題訪談問題／每一條招募條件，都能對應到框架裡的具體構念或 Objective
- 反向：框架裡的每個構念／Objective，都至少有一個對應的題目或資料蒐集項目——沒有的話要明確標出來，這代表訪談大綱有漏洞，不是無傷大雅的小事

**2. 嚴謹判準自我檢核（依技法所屬典範，套用對應的一組判準，不是套一套通用嚴謹清單就交差）**

| 技法典範 | 判準 |
|---|---|
| 質化訪談／日記研究法／情境訪查 | Lincoln & Guba 的 trustworthiness 四判準：可信度（Credibility）、可轉移性（Transferability）、可靠性（Dependability）、可確認性（Confirmability） |
| Research through Design 相關技法 | 中介層次知識（intermediate-level knowledge）是否明確、有沒有規劃 annotated portfolio 或反思紀錄機制，而不是做出原型就結束 |
| 混合方法 | 質化與量化資料之間的三角驗證邏輯講不講得通 |
| 可用性測試（走 `usability-test-planner`） | 沿用該 skill 既有的判準，不重複設計 |

agent 針對選定的技法，逐項自我檢核並寫下觀察（例如「可轉移性偏弱：招募條件過度侷限在單一族群，之後討論結果的可推論範圍要講清楚」），**這是提案不是結論**，你決定要不要因此調整設計。

## 4. 輸出

寫入該研究主題資料夾的 `04_研究方法/`：

- `研究方法_設計說明.md`——技法選擇的原因/限制/影響、雙向可回溯性對照表、嚴謹判準自我檢核結果（這是這個 agent 最重要的產出，是「為什麼這樣設計」的完整記錄）。**跟 Agent 5 的 `06_結果/04_對應研究框架.md` 不要搞混**：這份是資料蒐集**前**、「訪談題目 ↔ 框架構念」的設計檢查；Agent 5 那份是資料蒐集**後**、「Pattern ↔ 框架構念」的結果整理，方向跟時間點都不同，只是名字聽起來很像
- 依技法產生對應的執行文件，例如：
  - 半結構訪談／情境訪查 → `訪談大綱.md`
  - 日記研究法 → `日記提示設計.md`
  - 共同設計工作坊 → `工作坊流程.md`
  - 需要問卷的技法 → `問卷題項.md`（純 Markdown 表格呈現，不接外部表單系統）
- `招募條件.md`（不論哪個技法通常都需要）
- `研究倫理與同意書.md`（新增，強制產出不是選配）——IRB 需求評估、知情同意書重點、敏感資訊處理方式、招募文宣的用語考量

## 5. 已定案

- **表單製作**：不接 Google Forms／Notion 表單 API，`問卷題項.md` 就用純 Markdown 表格呈現，你自己口頭問或列印出來問都行，不用另外串接系統
- **執行階段發現嚴謹判準站不住腳時**：直接沿用 [研究架構Agent_SPEC.md](研究架構Agent_SPEC.md) 的 **Stage D（框架修正協作）**，不重複設計一套——不論是框架本身的構念/方法出問題，還是 Agent 4 這層的技法操作化出問題，都走同一套「先定位問題類型 → 給有憑有據的修正方向 → 你決定」的診斷式討論流程。差別只在於：框架層級的問題會回頭改 `03_研究架構/`，技法操作化層級的問題回頭改 `04_研究方法/`，但討論方式一致，不用學兩套
