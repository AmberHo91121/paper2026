## 1. 為什麼要重做

現有 `insight` skill 產出（如 [訪談分析_功能問題與AI工作流程洞見.md](../2026_DITL_Stytrix/第一次測試/訪談分析_功能問題與AI工作流程洞見.md)）品質已經到位，但停在 **①Raw Data + ②Context + 部分④Code**（「問題摘要」其實是 code，但沒有再往上收斂）。九層框架要求的 ⑤Theme～⑨Implication 完全沒做——也就是說，現有產出是「一份很好的逐字稿整理」，還不是「洞見報告」。這個 agent 要把這條路走完。

## 2. 九層分析框架（你指定）

| 層級 | 問題 | 產出 |
|---|---|---|
| ① Raw Data | 使用者說了什麼？ | Quote |
| ② Context | 什麼情況下說？ | 情境 |
| ③ Behavior | 使用者做了什麼？ | 行為 |
| ④ Code | 這段資料代表什麼？ | Code |
| ⑤ Theme | 哪些 Code 是同一類？ | Theme |
| ⑥ Pattern | 多個人／情境出現什麼規律？ | Pattern |
| ⑦ Why | 為什麼會有這個規律？ | 解釋 |
| ⑧ Insight | 這告訴我們什麼？ | Insight |
| ⑨ Implication | 設計應該如何回應？ | Design Opportunity |

**關鍵性質**：①→④是可回溯、貼著資料的「證據層」；⑤→⑥是機械式聚類，仍可回溯；⑦→⑨是**詮釋層，本質是假設**，agent 提出的東西必須明確標成「推論」而非「事實」，這是全流程唯一必須人工把關、不能自動化跳過的節點。

## 3. 觸發機制

三個 Stage 的觸發條件不同，因為依賴的資料範圍不同：

| Stage | 觸發條件 | 能不能逐份跑 |
|---|---|---|
| A 逐句編碼 | 單份逐字稿存在即可 | 可以，不用等其他受訪者，機械式逐份處理 |
| B 跨受訪者聚合 | **該 case 所有預計受訪者的 Stage A 都完成** | 不行，Pattern 判定要看跨受訪者重複性，少一位可能漏判或誤判 Pattern |
| C 詮釋 | 緊接在 Stage B 完成後自動接著跑 | — |

**誰來宣告「Stage B 可以跑了」**：目前沒有自動判斷機制——只有你知道這個 case 原本規劃要訪談幾位、有沒有臨時加人、資料是不是都到齊了，這個「宣告」必須是你明確說出來，不是 agent 自己猜的。

**已定案**：整條線是**手動觸發**——你把逐字稿彙整檔交給我、我判斷資料夠不夠、你確認要跑，我才執行。不接檔案監看機制（不偵測 `05_原始資料/*_逐字稿.md` 有新檔案就自動起 Stage A），這樣才跟整個工作流程其他 agent 的手動觸發原則一致，不會只有這裡自動化、其他地方都要你明確喊開始。

**已定案**：Stage B 的「所有受訪者到齊」由你口頭跟我說一聲即可（例如「這個主題的訪談都做完了，可以跑 Stage B」），不用另外在資料夾放訊號檔案——這件事本來就需要你判斷（原本規劃訪談幾位、有沒有臨時加人），加一個訊號檔案只是多一道手續，口頭講清楚就夠。

Stage C 產出後**必須停下來等你確認 Why**——這條規則不受觸發機制自動化與否影響，即使 Stage A/B 之後做成自動觸發，Stage C→人工確認這個關卡也不能拿掉。（原本這裡會接著講「不會自動往下接簡報生成 agent」，但那個 agent 已確認不需要，Stage C 產出就是整條鏈的終點）

**新增（補上反向的迴圈連結）**：如果你在 Stage A 逐句編碼的過程中，發現訪談大綱根本問不出有用的資料（例如某幾題受訪者普遍聽不懂、答非所問），這其實不是編碼層級的問題，是 [研究設計Agent_SPEC.md](研究設計Agent_SPEC.md)（Agent 4）技法操作化出了問題——一樣可以主動叫出 [研究架構Agent_SPEC.md](研究架構Agent_SPEC.md) 的 **Stage D（框架修正協作）**來討論，不用忍著把爛資料編碼完才反映。這條路之前只在 Agent 3/4 的文件裡單向提到，這裡補上反向的提醒。

## 4. Pipeline 設計：三階段

不做成單一步驟一次跑完，因為 ①-④（逐句處理）跟 ⑤-⑥（需要看到全體資料才能聚類）跟 ⑦-⑨（需要人判斷）的性質完全不同，混在一起會讓中間任何一層出錯都難以定位。

### Stage A — 逐句編碼（機械式，逐份處理）

- **輸入**：單份逐字稿
- **對每一個「值得記錄的觀察單位」**（不是每一句話，是每個訪談者判斷有資訊量的段落）萃取：
  - Raw Data：原文 + 時間戳（沿用現有格式 `[時間戳] 語者：「原文」`，不能編造引用——這條既有規則延續）
  - Context：當下在做什麼任務/討論什麼功能
  - Behavior：使用者當下的實際操作（不是只有語言，例如「重試了三次」「切換回 Photoshop」）
  - Code：這段代表的抽象標籤（例如「模糊輸入→AI過度發散」）
- **輸出**：單份逐字稿的編碼表（表格，一列一個觀察單位）
- **人工 review 點**：Code 的用字是否貼著資料、有沒有過度詮釋（Code 層還不該出現「為什麼」的判斷）

### Stage B — 跨受訪者聚合（機械式，全體批次）

- **輸入**：Stage A 產出的所有受訪者編碼表
- **做兩件事**：
  1. **Theme**：把語意相近的 Code 收斂成類別（例如「模糊輸入→AI過度發散」+「autoprompt遺漏需自行補充」→「AI在低約束輸入下的可控性落差」）
  2. **Pattern**：標出哪些 Theme 在多位受訪者/多個情境下重複出現，並附上每個 Pattern 底下有哪些受訪者、哪些 Code 支撐
- **輸出**：Theme 彙整表 + Pattern 清單（每個 Pattern 可回溯到底層 Code／Quote）
- **Pattern 判定門檻（已定案）**：至少 2 位不同受訪者、且分佈在 2 個不同情境/功能模組下出現同類 Code，才算一個 Pattern（沿用 StyTrix 範例已經示範的門檻）。只出現在同一人身上、或只在同一個情境下的重複，不算 Pattern，頂多記成「值得留意的個案觀察」附註在旁邊。樣本數很小的 case（例如少於 8 人）這個門檻可能太容易達到，agent 會額外註明「這個 Pattern 涵蓋了樣本的幾成」，讓你自己判斷夠不夠有代表性
- **人工 review 點**：Theme 分類是否把不相關的 Code 硬湊在一起；Pattern 涵蓋比例夠不夠有代表性

### Stage C — 詮釋（人機協作，非全自動）

- **輸入**：Stage B 的 Pattern 清單
- **對每個 Pattern**，agent 提出：
  - Why：**明確標註「推論」**——為什麼會出現這個規律的假設性解釋。**已定案**：如果資料支持不只一種合理解釋，agent 最多列出 2 個候選 Why（不是只能給一個），並排序哪個候選比較有支撐力、為什麼，由你選或提出第三種
  - Insight：這對使用者/產品代表什麼（如果 Why 有多個候選，Insight 也對應標出是哪個候選推導出來的，不要混在一起）
  - Implication：設計應該如何回應（具體可執行的方向，不是空泛的「應該改善使用者體驗」）
- **輸出**：Pattern 卡片（見第 4 節模板）
- **人工 review 點**：**Why 以上三層全部要你確認或修正**，agent 只提案，不能替你下結論——這是整個流程唯一允許 agent「猜」的地方，也是唯一規定必須人工覆核才能定稿的地方

## 5. 輸出文件結構（模板）

**已修正**：改成對應 [研究主題Repo_資訊架構.md](研究主題Repo_資訊架構.md) 的固定慣例，輸出到該研究主題資料夾底下的 `06_結果/`，不再自己另開 `洞見報告_<case名稱>/`：

```
06_結果/
  01_編碼總表.md        — Stage A 產出，逐受訪者，可回溯到原文
  02_Theme彙整.md        — Stage B 產出，Theme → 底下 Code → 涉及受訪者
  03_Pattern卡片.md      — Stage B+C 產出，每個 Pattern 一張卡：
                            Pattern描述 → 支撐證據(可展開回 Theme/Code/Quote)
                            → Why(推論,待確認) → Insight → Implication
  04_對應研究框架.md     — 新增：把上面的 Pattern 卡片依 03_研究架構（Agent 3 產出）裡的理論構念/Objectives 分類整理，
                            讓「結果」跟「框架」看得出對應關係，不是各自獨立產出的兩份東西
```

**跟 Agent 4 的 `04_研究方法/研究方法_設計說明.md` 不要搞混**：這份是資料蒐集**後**、「Pattern ↔ 框架構念」的結果整理；Agent 4 那份是資料蒐集**前**、「訪談題目 ↔ 框架構念」的設計檢查，方向跟時間點都不同，只是名字聽起來很像。

Pattern 卡片範例格式：

```markdown
### Pattern：低約束輸入下的可控性落差

**涉及**：Lory（Concept Creator / Mix & Match）、Rocco（Model Library autoprompt）
**支撐 Theme**：AI在低約束輸入下的可控性落差
**支撐 Code**：模糊輸入→AI過度發散、autoprompt遺漏需自行補充

**Why（推論，待你確認）**：
服裝設計發想階段的方法論本來就是「先粗略、後收斂」，受訪者的模糊輸入是刻意的工作方式而非能力不足；
但 AI 沒有機制區分「模糊=邀請發想」vs「模糊=需要猜測」，預設走向後者。

**Insight**：
對這群使用者而言，「精準控制」與「保留驚喜空間」不是二選一，而是取決於工作流程的階段；
問題核心不是 AI 腦補能力不夠，而是 AI 無法辨識當下使用者是否「想要」被腦補。

**Implication（設計機會）**：
提供明確的模式切換（如「發想模式／規格模式」），讓使用者標註這次輸入是刻意模糊還是精準規格，
而不是要求使用者反過來學習如何用 prompt 寫法暗示 AI「不要腦補」。
```

## 7. 已定案事項小結

- **Pattern 判定門檻**：2 位不同受訪者＋2 個不同情境，樣本小的 case 額外標涵蓋比例（見第 4 節 Stage B）
- **Why 的呈現方式**：最多 2 個候選，排序＋由你選（見第 4 節 Stage C）
- **觸發機制**：手動觸發、口頭宣告 Stage B 可以跑了、可以反向觸發 Agent 3 的 Stage D（見第 3 節）
